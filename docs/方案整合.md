# 方案整合

方案以 **汇报 PPT 的设计为准**（笔记本购买决策 · A/B/C 三条件 · 8 个任务）。本文件记录：这个设计从哪里来、外部调研中哪些东西被吸收进来、哪些被明确排除。

---

## 一、主线：PPT 方案

```
用户需求（预算 / 用途 / 限制）
        ↓
OxyGent 多智能体：检索 | 性能 | 成本 | 风险 | 主控
        ↓
购买建议（结论 + 证据 + 分歧 + 执行记录）
        ↓
A 单个 Agent ｜ B 多个 Agent ｜ C 多个 Agent + 人
```

- 自变量：**协作的人数，以及人在不在场**
  - A → B：只增加 Agent 数量
  - B → C：只增加"人在场"，C 复用 B 的同一次多 Agent 运行结果
- 场景：7000 元预算的计算机专业学生买笔记本
- 指标：任务成功率、推荐质量、完成时间、干预次数、错误发现率、纠错成功率、信任、掌控感、NASA-TLX、SUS
- 假设：H1（B 优于 A 但有上限）、H2（C 提升监督）、H3（C 有额外负担）

### 明确不吸收的部分

| 不吸收 | 原因 |
|---|---|
| MetaJD 的代码 | 24 个 Agent 一次性注册进同一个 `oxy_space`，无路由无裁剪，是"设计过度复杂"的反面教材 |

## 三、为 PPT 方案补的效度基础

PPT 原方案里最难落地的是「推荐质量」——买笔记本这件事本身没有标准答案。我们的处理：

1. **模拟商品库**（`taskset/catalog.json`）：8 款虚构机型，明示"教学用、非真实商品"。
2. **双套参数**：每款机型同时有 `listed`（商品页标称）与 `actual`（实际）。两者不一致即「陷阱机型」：
   - `YZ-A16`：标称 16GB 内存，实际 8GB
   - `PS-T15`：标称 5299 元（上月活动价快照），实际 5999 元
3. **约束求解出金标**：`scripts/build_taskset.py` 用 `actual` 值求解，要求每个任务**恰好 1 个解**，否则报错退出。金标不手写，避免人工写错。

这样"正确"就是可判定的：**用户是否选中唯一满足全部硬约束的机型**。同时，系统若采信 `listed` 值，就会推荐违反约束的机型——**错误是"自然产生"的，不是人为植入的**。

另外增加一个**无解任务**（T08：预算 5000 + 独显 + ≤2kg），正确答案是「无合适机型」，用来测系统会不会硬推一个违反约束的机型。

## 四、数据链路

```
taskset/catalog.json   （商品库：listed + actual + 陷阱标注）
taskset/decision_tasks.json  （8 个任务的约束）
        │
        │ scripts/build_taskset.py  —— 求解并校验金标唯一
        ▼
taskset/experiment_tasks.json   （金标 + 约束文本 + 陷阱诱饵清单）
        │
        │ src/oxyagents/make_fixtures.py   （需要 LLM API key）
        ▼
fixtures/<task_id>/{A,B,C}.json   ←── src/adapters/trace_to_session.py
        │                              （也可直接转换 OxyGent 真实 trace）
        ▼
src/experiment/server.py ──→ web/ 三条件界面 ──→ data/logs/*.jsonl
```

## 五、三条件的实现约束（效度红线）

| 要求 | 实现方式 |
|---|---|
| B 与 C 的 Agent 数据完全一致 | 两者复用同一次多 Agent 运行结果，仅 `condition` 字段不同；C 额外挂 `interactions` 协作点，不影响 Agent 结论 |
| A 是真的单 Agent | A 由单 Agent 独立运行生成，不是"把多 Agent 结果裁掉过程" |
| 商品信息对被试一致 | `/api/catalog` 只下发 `listed` 值，`actual` 值仅用于服务端判分，不泄露给被试 |
| 用户看不到评分依据 | `task.answer`、`error_markers` 不下发到前端 |

## 六、明确不做的事

1. 不 fork 那两个参赛仓库的代码。
2. 不引用其宣称的准确率数字。
3. 不把大附件或日志提交进仓库。
4. 不在实验期实时跑 Agent（B 与 C 会因随机性而不一致）。
5. 不为"看起来更厉害"增加 Agent 数量或界面复杂度。
