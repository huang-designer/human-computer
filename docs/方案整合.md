# 方案整合

把三处来源合成一条可执行的路线：赛题数据集（真实任务与标准答案）、两个开源参赛仓库（架构与反面教材）、OxyGent 官方能力（trace 与可视化）。

---

## 一、四个来源及其取舍

| 来源 | 拿到什么 | 用不用 |
|---|---|---|
| **赛题验证集**（经 MetaJD 仓库获取） | 100 条任务，含 `query / level / answer / steps`，level 1/2/3 分布 42/43/15 | ✅ **直接用**。这是全项目最关键的资产：答案客观，成功率可字面测量 |
| **MetaJD**（★3，387 MB） | 24 个 Agent 的角色清单（planner / executor / browser / song_recognition …）、数据集 | ⚠️ **只取数据与角色灵感**。24 个 Agent 全注册进一个 `MAS`，是"设计过度复杂"的活标本，不可复用代码 |
| **OG-A-MAS**（★0） | 分层监督架构：Orchestrator / Specialist / **Auditor** / Reviewer；闭环返工；格式化品控 | ✅ **取架构思想**。文档宣称 60–70% 准确率，实测其提交结果在 10 条验证样本上仅 1/10 —— 所有数字都不可引用 |
| **OxyGent 官方** | 真实 trace 结构（`app_trace` / `app_node`，含 caller/callee/father_node_id/耗时/state）、自带 Web UI（Mermaid 节点图）、HITL 示例 | ✅ **取基础设施**。但**官方没有赛题 baseline**，`grep 挑战赛` 零命中 |

## 二、赛题真实形态（推翻原始设想）

原 `选题调研.docx` 与 PPT 假设的是「用户买笔记本，多个 Agent 分别比较候选商品，用户做最终选择」。

**赛题实际不是这个。** 它是 GAIA 式基准：

| 项 | 实际 |
|---|---|
| 任务 | 回答有唯一确定答案的复杂问题 |
| 评测 | 完全匹配准确率（准精确匹配） |
| 附件 | PDF / PPTX / XLSX / 图片 / 音频 / 视频 |
| 难度 | level 1 单步推理；level 2 多工具；level 3 多步规划 + 跨源整合 |
| 答案类型 | number 41 / short 33 / text 23 / url 2（验证集） |

典型题目：金条支付（答案 `3`）、毒兔检测（`6`）、"视频里鼠标最后停在哪"（`加入购物车`）、"该商品生产商总部附近最近的带'技术'的研究院"（`中国空间技术研究院`）。

**所以用户角色从「决策者」改成「答案审核者」**：看 Agent 给答案与过程，判断是否接受、错在哪一步。这个改动让实验**更容易做也更有力**——错误发现率不再依赖主观评分，而是「AI 答错时用户是否拒收」。

## 三、最终系统架构

```
                       ┌──────────────────────────────┐
            task       │      master_agent（主控）     │
              │        │  分配 → 汇总 → 处理分歧 → 输出 │
              ▼        └───────────────┬──────────────┘
   ┌──────────────────┬────────────────┼──────────────┬──────────────────┐
   ▼                  ▼                ▼              ▼                  │
search_agent      reader_agent     code_agent    verify_agent           │
检索来源           读附件抽事实      计算核对       质疑 / 不产出答案      │
   │                  │                │              │                  │
   └──────────────────┴────────────────┴──────────────┴──────────────────┘
                                   │
                          trace / Session 归一化
                                   │
              ┌────────────────────┴────────────────────┐
              ▼                                         ▼
      条件 A：只显示答案                      条件 B / C：同一份 Session
      （单 Agent 运行）                        B 隐藏过程 · C 显示过程
```

### 角色纪律

- **5 个角色上限**。超过 5 个，时间会花在调框架上，而不是做 HCI 研究。
- **校验与生成分离**。`verify_agent` 不产出答案，只质疑。它既是质量手段，也是 C 条件「分歧」区块的数据来源（借自 OG-A-MAS 的 Auditor / Reviewer 分层）。
- **舍去不做**：不加 `song_recognition_agent`、`stock_agent` 这类专用 Agent（MetaJD 的 24 角色清单里有一半属于此类），它们对研究问题没有增量。

### 三条件的实现约束

| 条件 | 数据 | 界面 |
|---|---|---|
| A | 单 Agent 独立运行的输出 | 只显示最终答案 |
| B | 多 Agent 运行的输出 | 只显示最终答案（过程存在但不展示） |
| C | 与 B **完全相同**的多 Agent 输出 | 显示 Agent 卡、时间线、证据、分歧 |

**B 与 C 的 fixture 除 `condition` 字段外必须逐字节相同**，否则差异不能归因于界面。`scripts/make_demo_fixtures.py` 里对此有断言式说明，`fixtures/sample.json` 也满足该约束。

## 五、与研究问题的映射

| 研究问题 | 由哪个模块支撑 | 对应指标 |
|---|---|---|
| RQ1 多 Agent 是否真的更准 | A vs B 的 fixture（可离线批量比对，无需真人） | 完全匹配准确率 |
| RQ2 可见性是否提升监督 | B vs C 界面 | 错误发现率、纠错成功率 |
| RQ3 收益是否抵得上负担 | B vs C 行为日志 | 完成时间、展开证据次数、任务后负荷评分 |
| RQ4 是否诱发过度信任 | 采纳率 × 正确率的交叉 | 高采纳 + 低发现的组合 |

**注意 RQ1 不该在用户实验里测**：A 与 B 的答案质量差异用 100 条验证集离线跑一遍就有统计力，塞进 n=24 的用户实验只会浪费被试时间。用户实验只保留 A vs C（或不含 A），把精力放在交互效应上。

## 六、明确不做的事

1. 不 fork 那两个仓库的代码。它们的价值是「知道别人做了什么、没做什么」，不是可复用的实现。
2. 不引用任何开源仓库宣称的准确率数字（包括我实测的 10%——样本太小，只说明它们没做严谨评测）。
3. 不把 380 MB 的附件塞进仓库。只提交 `task_id` 列表 + 拉取脚本。
4. 不做实时 Agent 运行作为实验条件。离线预生成是保证 B/C 内容一致的唯一可靠方式。
5. 不为了"看起来更厉害"增加 Agent 数量或界面复杂度。
